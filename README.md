# Annuva

**Self-hostable billing and profitability dashboard for freelancers and small agencies that sell
recurring services – hosting, domains, maintenance – next to their project work.**

Annuva keeps customers, recurring charges, fixed costs, expenses, resources, offers and invoices in
one place. It answers the questions a spreadsheet makes hard: *What did I earn this year? What is
coming in and going out next month? Which customer is actually worth it? How much tax should I put
aside?*

- Self-hosted for free under the AGPL – one Docker container, SQLite by default
- Bilingual UI (English, German), light and dark theme, works on every screen size
- REST API with personal bearer tokens and a built-in MCP server for AI assistants

## Features

**Dashboard**

- Key figures: revenue, expenses, result, estimated tax, result since start, recurring revenue and
  fixed costs per year, server coverage, invoices to issue, open tasks
- Revenue and expenses per year, including a *plan year* built from recurring charges and fixed costs
- Monthly cash flow with planned values and the cumulative balance
- Per customer: revenue, costs, recurring surplus after domains, packages and a share of the server
  costs – and a rating whether the customer is worth it
- Fixed costs by assignment, expenses by category and year, tax estimate per year
- Upcoming items: invoices to issue, recurring invoices, planned costs and contract renewals
- Filter everything by year and customer

**Business data**

- Customers with a step-by-step wizard (master data, billing, recurring charges, resources, fixed
  costs, offers) and a detail page with everything that belongs to the customer
- Customers can be archived once they have no recurring charges left
- Partners (agencies) that receive one combined invoice for several end customers
- Recurring charges (monthly, quarterly, half-yearly, yearly), fixed costs with renewal dates,
  one-off expenses with receipts
- Resources (domains, containers, proxy hosts, databases, …) per customer
- Offers as uploaded PDFs with number, dates, amount and status
- Tasks with due dates and status

**Invoices**

- Drafts by hand or generated by the *billing run* from due recurring charges – grouped per
  customer, or per partner for partner customers
- Gapless invoice numbers per year with a configurable pattern (`RE-{YYYY}-{NNN}`)
- PDF generation with configurable invoice templates (logo, texts, footer, colour, payment terms,
  scanned signature) and a live preview while editing
- Issued invoices are immutable; corrections are made with a cancellation invoice
- Small-business taxation (§ 19 UStG) or regular VAT with per-line tax rates
- Send invoices and payment reminders by e-mail directly from the app

**Accounts and integration**

- Users with the roles *admin* and *user*; e-mail and password login, password reset by e-mail
- Passwords need at least 9 characters with upper-case and lower-case letters and a digit;
  special characters are allowed but not required
- Profile picture upload with Gravatar fallback; language, time zone and theme per user
- Optional two-factor authentication with an authenticator app (TOTP) and one-time recovery codes;
  admins can reset it for users who lost their device
- Personal API tokens (read or read/write) for the REST API and the MCP server
- OpenAPI 3.1 description of the complete API

## Quick start with Docker

```yaml
# compose.yaml
services:
    annuva:
        image: ghcr.io/dasred/annuva-app:latest
        container_name: annuva
        restart: unless-stopped
        ports:
            - "40100:40100"
        volumes:
            - ./data:/var/www/data
        environment:
            # Optional – see "Configuration"
            SMTP_HOST: smtp.example.com
            SMTP_USER: annuva@example.com
            SMTP_PASSWORD: secret
            MAIL_FROM: annuva@example.com
```

```bash
docker compose up -d
docker compose logs annuva | grep -A1 "Setup required"
```

Open `http://localhost:40100`, enter the setup token from the log and follow the wizard.

Put a reverse proxy with TLS in front of it for anything beyond `localhost`. Annuva takes its public
URL from the request (`X-Forwarded-Host` / `X-Forwarded-Proto`), so it works under any domain
without configuration.

The data directory must be writable by the container user (`node`, uid 1000):

```bash
mkdir -p data && sudo chown 1000:1000 data
```

## Configuration

Everything is configured with environment variables (or a `.env` file in development). **Every
variable is optional** – without any configuration Annuva starts as a single-tenant instance with
SQLite in `./data`. See [`.env.example`](.env.example).

| Variable               | Default            | Description                                                                                           |
|------------------------|--------------------|-------------------------------------------------------------------------------------------------------|
| `APP_MODE`             | `single`           | `single`: self-hosted with setup wizard. `multi`: several tenants with self-registration (prepared).  |
| `APP_NAME`             | `Annuva`           | Name shown in the UI and in e-mails.                                                                  |
| `APP_URL`              | –                  | Public URL. Only needed for links in e-mails sent without a request; otherwise taken from the request. |
| `HOSTNAME`             | `0.0.0.0`          | Listen address.                                                                                       |
| `PORT`                 | `40100`            | Listen port.                                                                                          |
| `DATA_DIR`             | `./data`           | Database (SQLite), uploaded files, invoice PDFs and generated secrets.                                |
| `DB_DRIVER`            | `sqlite`           | `sqlite`, `mysql` or `postgres`.                                                                      |
| `DB_SQLITE_FILE`       | `annuva.sqlite`    | SQLite file, relative to `DATA_DIR`.                                                                  |
| `DB_HOST`              | `localhost`        | MySQL/Postgres host.                                                                                  |
| `DB_PORT`              | `3306` / `5432`    | MySQL/Postgres port.                                                                                  |
| `DB_NAME`              | `annuva`           | Database name.                                                                                        |
| `DB_USER`              | `annuva`           | Database user.                                                                                        |
| `DB_PASSWORD`          | –                  | Database password.                                                                                    |
| `DATABASE_URL`         | –                  | Alternative to the `DB_*` values, e.g. `postgres://user:pass@host/db`.                                |
| `AUTH_SECRET`          | generated          | Secret for session and token hashes. Generated into `DATA_DIR/.auth-secret` when empty.               |
| `SETUP_TOKEN`          | generated          | Protects the setup wizard. Generated and printed to the log when empty.                               |
| `SESSION_MAX_AGE_DAYS` | `30`               | Lifetime of a login session.                                                                          |
| `SMTP_HOST`            | –                  | SMTP server. Without it no e-mails are sent (password reset, invoices, reminders are disabled).        |
| `SMTP_PORT`            | `587`              | SMTP port.                                                                                            |
| `SMTP_SECURE`          | `false`            | `true` for implicit TLS (port 465).                                                                   |
| `SMTP_USER`            | –                  | SMTP user.                                                                                            |
| `SMTP_PASSWORD`        | –                  | SMTP password.                                                                                        |
| `MAIL_FROM`            | –                  | Sender address. Mails go out as `"<Company> via Annuva" <MAIL_FROM>` with the company e-mail as Reply-To. |
| `GRAVATAR_ENABLED`     | `true`             | Use Gravatar when a user has no profile picture.                                                      |
| `DEFAULT_LOCALE`       | `en`               | Language for new users when the browser language is not supported (`de`, `en`).                     |
| `DEFAULT_TIMEZONE`     | `Europe/Berlin`    | Time zone for new users.                                                                              |
| `UPLOAD_MAX_SIZE`      | `20MB`             | Maximum upload size (`B`, `KB`, `MB`, `GB`).                                                          |
| `LOG_LEVEL`            | `info`             | `debug`, `info`, `warn` or `error`.                                                                   |

Invalid values stop the server at start with a message naming the variable.

## First start: the setup wizard

On the first start of a single-tenant instance the database is empty and every page redirects to
`/setup`. The wizard is protected by the setup token from the log (or `SETUP_TOKEN`) and walks
through:

1. **Setup token**
2. **Database** – checks the connection configured in the environment and applies the migrations
3. **Administrator** – the first user
4. **Company** – name, address, contact, tax mode (small business or regular VAT), bank details,
   invoice number pattern
5. **Invoice template** – letterhead, footer, payment terms
6. **Customers** – optionally create the first customers right away

After the setup the wizard is locked; the token is no longer accepted.

## Concepts

**Amounts and taxes.** All amounts are entered and shown in the currency of the instance. With
small-business taxation (§ 19 UStG) invoices carry no VAT and the matching note; with regular
taxation each line has its own tax rate. The tax estimate on the dashboard multiplies the yearly
profit (plus manual adjustments) with the marginal tax rate you store per year – it is an estimate,
not tax advice.

**Customer rating.** For every customer Annuva computes the recurring surplus per year: recurring
charges minus domains and packages that are passed through, minus the customer's share of the
server costs. The share is split equally among all customers with hosting (configurable in the
settings). Customers with a positive surplus are *worth it*; own projects and internal entries are
shown separately.

**Invoice lifecycle.** `to_issue` (draft, freely editable) → `open` (issued: number, date, PDF and
snapshot are fixed) → `paid`. An open or paid invoice can only be cancelled; the cancellation is a
new invoice with negative amounts that references the original.

**Billing run.** Collects all recurring charges due until a date, creates one draft per recipient
and moves each charge to its next invoice date. Running it twice does not create duplicates.

**Files.** Uploads and generated PDFs are stored under `DATA_DIR/files/ab/cd/<sha256>`; the original
file name lives in the database. Files are only delivered to users of the owning tenant.

## REST API

All business data is available under `/api/v1`. Authenticate with a personal API token, created in
*Profile → API tokens*:

```bash
curl -H "Authorization: Bearer an_…" https://annuva.example.com/api/v1/customers
```

Tokens belong to their user and have the same permissions as that user. Two-factor authentication
protects the login in the browser; API tokens are separate credentials and are not affected. A token has the scope `read`
or `read_write` and may expire. In the browser the session cookie works as well.

| Endpoint                                     | Description                                                     |
|----------------------------------------------|-----------------------------------------------------------------|
| `GET /api/v1/{entity}`                       | List with `q` (search), `sort`, `order`, `limit`, `offset`, `includeArchived` and field filters |
| `POST /api/v1/{entity}`                      | Create                                                          |
| `GET/PATCH/DELETE /api/v1/{entity}/{id}`     | Read, update, delete                                            |
| `POST /api/v1/customers/{id}/archive`        | Archive or restore a customer                                   |
| `GET/POST /api/v1/invoices`                  | Invoices with their lines                                       |
| `POST /api/v1/invoices/{id}/{action}`        | `issue`, `pay`, `reopen`, `cancel`, `send`, `remind`            |
| `GET /api/v1/invoices/{id}/pdf`              | Invoice PDF (preview for drafts)                                |
| `POST /api/v1/billing/run`                   | Billing run (`dryRun` for a preview)                            |
| `GET /api/v1/dashboard`                      | All dashboard figures (`year`, `customerId`); amounts in cents  |
| `POST /api/v1/files`, `GET /api/v1/files/{id}` | Upload and download files                                     |
| `GET/PATCH /api/v1/settings`                 | Company settings (admins)                                       |
| `GET /api/v1/openapi`                        | OpenAPI 3.1 description                                         |

Entities: `customers`, `partners`, `resources`, `offers`, `recurring-charges`, `recurring-costs`,
`expenses`, `tasks`, `tax-years`, `tax-adjustments`, `invoice-templates`.

Money values in entity endpoints are decimals (`60.5`); the dashboard returns integer cents. Errors
are JSON with `error`, `message` and, for validation errors, `fields`.

The complete, always up-to-date reference is the OpenAPI document at `/api/v1/openapi`.

## MCP server

Annuva contains a [Model Context Protocol](https://modelcontextprotocol.io) server at `/api/mcp`
(Streamable HTTP, stateless). It authenticates with the same API tokens and offers tools for
everything the REST API does: list, get, create, update and delete for every entity, invoices and
their actions, the billing run and the dashboard. Tokens with the scope `read` only see the
read-only tools.

Example for Claude Code:

```bash
claude mcp add --transport http annuva https://annuva.example.com/api/mcp \
    --header "Authorization: Bearer an_…"
```

Any MCP client that supports Streamable HTTP with custom headers works the same way.

## Data, backups and updates

Everything worth keeping is in `DATA_DIR`: the SQLite database, all files and the generated
secrets. Back up the whole directory. For a consistent SQLite copy while the app is running use
`sqlite3 data/annuva.sqlite ".backup backup.sqlite"`, or stop the container briefly.

With MySQL or Postgres back up the database as usual, plus `DATA_DIR` for the files.

Updates: pull the new image and restart. Database migrations run automatically on start.

## Development

Requirements: Node.js ≥ 26.12 and npm ≥ 11.20.

```bash
npm install
cp .env.example .env    # optional
npm run dev             # http://localhost:40100
```

| Script              | Description                                         |
|---------------------|-----------------------------------------------------|
| `npm run dev`       | Development server on port 40100                    |
| `npm run build`     | Production build (`.next/standalone`)               |
| `npm start`         | Run the production build                            |
| `npm test`          | Type check, lint and all tests                      |
| `npm run typecheck` | TypeScript (`tsc --noEmit`)                         |
| `npm run lint`      | Oxlint                                              |
| `npm run test:watch`| Vitest in watch mode                                |

**Stack:** Next.js (App Router), React, TypeScript, Tailwind CSS, Kysely (SQLite via the built-in
`node:sqlite`, MySQL, Postgres), zod, @react-pdf/renderer, nodemailer, the MCP TypeScript SDK and
Vitest.

**Structure**

```
src/
    app/            Routes: pages (app), (auth), setup and the API under app/api
    calculation/    Pure dashboard calculations (tested without a database)
    client/         Browser helpers: API client, hooks
    component/      React components, one per file
    entity/         Entity definitions – drive database access, validation, API, MCP, OpenAPI and forms
    i18n/           Translation runtime
    server/         Services: auth, database, invoices, billing, PDF, mail, MCP, OpenAPI, …
    translations/   de/ and en/ – plain key/value objects
    validation/     Rules shared by server and browser (password policy)
test/               Vitest: calculations, helpers and an SQLite integration test
```

**Conventions**

- Formatting follows the IntelliJ code style of the project: 4 spaces, single quotes, semicolons,
  trailing commas in multiline literals, `else`/`catch`/`finally` on a new line, always braces,
  aligned object values. Reformat in IntelliJ before committing.
- One interface, class or component per file; only `export default` (except the named exports
  Next.js requires in routes, pages and layouts).
- ESM only; code, comments and documentation in English.
- Every UI text lives in `src/translations/{de,en}`; the German dictionary is typed against the
  English one, so missing keys fail the type check.
- Amounts are stored as integer cents, percentages and quantities as integer hundredths, dates as
  `YYYY-MM-DD`.
- Commits follow [Conventional Commits](https://www.conventionalcommits.org) – they drive the release.

**Adding a field or an entity.** Extend the definition in `src/entity/definitions`, add a
migration in `src/server/db/migrations` and the translations. Database access, validation, the REST
endpoints, the OpenAPI document, the MCP tools and the forms pick it up automatically.

## Releases and deployment

Development happens on `develop`; `main` is released. Every push to `main` runs the pipeline:
tests, build, [semantic-release](https://semantic-release.gitbook.io) (version, changelog, GitHub
release, back-merge into `develop`), the Docker image `ghcr.io/dasred/annuva-app` and the
deployment. The version is shown in the user menu.
